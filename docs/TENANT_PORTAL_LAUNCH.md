# Tenant portal launch

The app includes separate tenant password accounts at `/tenant`, account grants and revocation in the admin tenant view, recurring-charge preview/post controls, and Stripe Checkout integration. Stripe remains disabled until its credentials and webhook are connected. Admins can prepare an activation link or explicitly send an invitation or password reset email. The UI distinguishes prepared links, provider acceptance, unconfigured delivery, and failure; provider acceptance does not confirm inbox delivery. Tenant recovery returns the same response for known and unknown eligible addresses.

The replacement deployment target is the separate Replit `5Central-New` app at `https://5-central-new.replit.app`. The original app is unchanged. Launch requires reviewed host session schema, Rent Ops migrations 1–23, distinct database roles, a verified Rent Ops data import, private object storage, and the required production environment values described in `RENDER_DEPLOYMENT.md`. Startup checks those requirements and does not migrate or substitute demo data. Replacement database and provider provisioning are in progress; publishing has not yet passed production readiness. A stored sandbox key does not enable live payment collection.

After deploying, confirm `/healthz` and `/readyz`, authenticate the operator, reconcile tenant/unit associations, then create an account grant for an exact person and tenancy. Use Send invitation for a pending account or Send password reset for an active account. Tokens are single-use and existing credentials remain valid until a reset is consumed. Lease downloads expose only verified PDFs with exact person, tenancy, property, and unit ownership. Test activation, login, logout, password change, revocation, and cross-tenant denial against staging before inviting residents.

To connect payments, set `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, and the existing `RENT_OPS_PUBLIC_APP_URL` to the HTTPS app origin (`TENANT_PORTAL_ORIGIN` is an optional override). Configure Stripe to send Checkout completion/async success/async failure/expiry, PaymentIntent success/processing/failure/cancellation, refund updates, and dispute events to `/api/tenant/payments/webhook`. Start with test credentials and verify duplicate and delayed events before selecting live credentials. A browser return does not post payment; verified provider events control payment state. Card and ACH processing, posted credits, and bank settlement are separate states.

Run `npm run check`, `npm run test:rent-ops`, and `npm run build` for local validation. Run `NODE_ENV=development npx tsx --no-cache scripts/tenant-flow-qa.ts` for the isolated application → submitted → approved → future tenancy → move-in → tenant account workflow. It also checks invitation/reset delivery to a local sink, password lifecycle, own-lease download and cross-tenant denial, recurring billing, and simulated payment event replay.

Add `--serve` to retain that synthetic workflow at `http://127.0.0.1:4176/qa` for browser review after a standard build. The landing page identifies the synthetic accounts. The harness uses in-memory PGlite, local email and document stores, and a fake payment provider by default; it binds only to loopback. Stop the process to discard its accounts and sessions. Real Stripe sandbox testing is a separate explicit opt-in launcher and requires a test key; live keys and production mode are rejected.

For Replit-managed tenant email, set `RENT_OPS_TENANT_EMAIL_ENABLED=true`, `RENT_OPS_TENANT_EMAIL_PROVIDER=replit-gmail`, `RENT_OPS_GMAIL_FROM`, and the HTTPS `RENT_OPS_PUBLIC_APP_URL`. The pinned `@replit/connectors-sdk` 0.4.3 uses the platform Gmail proxy; the target app must have the connector grant available at runtime. A connected account in the UI alone does not prove a sent message. The selected Gmail provider also delivers applicant resume links. Webhook mode remains available when a separately configured receiver is used.
