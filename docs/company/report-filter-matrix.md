# Rental report filter matrix

This matrix is the executable filter discovery contract for the eleven available rental reports. The definitions in `shared/report-filter-definitions.ts` are the source used by the report catalog, the browser setup flow, REST discovery, and Codex discovery. A report setup renders these fields before execution; the selected values are sent to the existing report engine when the caller runs the report.

The catalog defaults are suggested setup/request presets. They do not rewrite the behavior of an omitted field in the existing domain service. A caller that needs the same result as the suggested setup must send the default explicitly. In particular, `propertyScope=active` is the manager setup preset; callers that omit it continue to receive the existing transport or domain behavior for that surface.

`propertyScope` and `propertyIds` are available on every report. `propertyScope` has the options `active` (default preset) and `all`. `propertyIds` is a multi-value property reference; `propertyId` is its accepted single-value API alias, so clients should render one Properties control. An empty property selection means no explicit property narrowing. Reference values are resolved from the caller's authorized directory and are never embedded in the static catalog.

| Report | Available fields after the common property scope | Date semantics | Suggested presets and report-specific options |
| --- | --- | --- | --- |
| `rent-roll` | `unitId`, `occupancy`, `readiness`, `listing`, `balanceStatus`, `search` | `asOfDate` is an inclusive unit/account observation date | `occupancy=[current]`, `balanceStatus=all`; occupancy: `current`, `future_preleased`, `vacant`, `unknown`; readiness: `ready`, `not_ready`, `off_market`; listing: `listed`, `unlisted`, `off_market`; balance: `all`, `due`, `credit`, `zero`, `unverified` |
| `occupancy` | `unitId`, `occupancy`, `readiness`, `listing` | `asOfDate` is an inclusive occupancy observation date | `occupancy=[vacant]`; occupancy: `current`, `future_preleased`, `vacant`, `unknown`; readiness: `ready`, `not_ready`, `off_market`; listing: `listed`, `unlisted`, `off_market` |
| `scheduled-income` | `unitId`, `tenantStatus`, `search` | `month` selects the scheduled month; `asOfDate` controls the dated observation/configuration boundary | `tenantStatus=current`; tenant status: `all`, `current`, `former`, `future`, `unknown` |
| `collected-income` | `unitId`, `tenancyId`, `personId`, `tenantStatus`, `search` | `month` selects receipt month, or `fromDate`/`toDate` selects an inclusive receipt/activity range; the month and range controls are mutually exclusive; `asOfDate` is the inclusive allocation visibility cutoff | `tenantStatus=current`; tenant status: `all`, `current`, `former`, `future`, `unknown` |
| `scheduled-vs-collected` | `unitId`, `tenantStatus`, `search` | `month` selects the comparison month; `asOfDate` is the inclusive observation/cutoff boundary | `tenantStatus=current`; tenant status: `all`, `current`, `former`, `future`, `unknown` |
| `delinquency` | `unitId`, `tenantStatus`, `balanceStatus`, `search` | `asOfDate` is the inclusive account balance cutoff | `tenantStatus=current`, `balanceStatus=due`; balance: `all`, `due`, `credit`, `zero`; tenant status: `all`, `current`, `former`, `future`, `unknown` |
| `tenant-ledger` | `unitId`, `tenancyId`, `personId`, `tenantStatus` | `fromDate`/`toDate` select an inclusive ledger activity range; `asOfDate` is the inclusive ledger cutoff; a range beginning with `fromDate` adds a report-only opening balance row | `tenantStatus=current`; tenant status: `all`, `current`, `former`, `future`, `unknown` |
| `lease-expiration` | `tenantStatus`, `status`, `search` | `asOfDate` is the inclusive lease observation date; `status=expiring` means the engine's fixed 90-day lookahead from that date | `tenantStatus=current`; lease action status: `expiring`, `month_to_month`, `not_due` |
| `security-deposit` | `unitId`, `tenantStatus`, `search` | `asOfDate` is the inclusive deposit receipt/disposition cutoff | `tenantStatus=current`; tenant status: `all`, `current`, `former`, `future`, `unknown` |
| `applicant-pipeline` | `status`, `search` | `asOfDate` is the inclusive stage-age observation date used for `daysInStage` | Application status: `complete`, `in_progress`, `awaiting_payment`, `draft`, `submitted`, `missing_information`, `under_review`, `approved`, `declined`, `withdrawn`, `converted` |
| `hap` | `tenantStatus`, `status`, `search` | `month` selects the effective HAP month; `asOfDate` is the inclusive receipt visibility cutoff | `tenantStatus=current`; HAP contract status: `active`, `ended`, `exception`; `pending` is source-valid but excluded by the existing HAP report engine |

The API `status` field is always a string array. The catalog therefore marks lease action, application, and HAP status controls as multi-select fields even when a caller chooses one value. `occupancy`, `readiness`, and `listing` are also arrays. `tenantStatus`, `balanceStatus`, and `propertyScope` are scalar controls. Clients should omit an unselected multi-select field; an empty array is not a universal “all” contract because the existing engines differ in how they treat an empty array.

The catalog deliberately does not expose filters that the corresponding engine ignores: lease type, unit/person/tenancy selectors on lease expiration, person/tenancy selectors on HAP and applicant pipeline, person selectors on delinquency's default balance path, search on occupancy or tenant ledger, or a month selector on tenant ledger. Planned catalog entries have no filter definitions until an executable report engine and parity tests exist.

Future financial, project, task, and investor reports follow the same setup-first rule. Their definitions may include entity, property, unit, project, account, date, basis, status, person, vendor, scenario, and grouping controls only when the corresponding engine supports and validates that field. Dependent controls should narrow from the selected parent context, and the same validated server filters must be discoverable through the browser catalog, REST, and Codex surfaces. A planned catalog entry stays without runnable filter metadata until its engine, dependent-control behavior, and discovery/execution parity are implemented.
